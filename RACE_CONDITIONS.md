# Race conditions and fixes

Reviewed before implementation changes for this task. The fixes below are the minimum safeguards needed to keep one user action attached to the correct job, turn, selection, and demo mode. Some storage protections already existed; those are recorded so they remain covered by checks.

| Race | Files involved | Fix | Check |
| --- | --- | --- | --- |
| Two identical `/api/tryon` requests can both miss the result cache and start separate Replicate predictions. A voice `start_tryon` request can collide with the photo UI request in the same way. | `src/app/api/tryon/route.ts`, `src/lib/tryon-jobs.ts`, `src/app/api/voice-tools/[...tool]/route.ts`, `python-agent/tools.py` | Reserve the normalized image hash with the existing atomic Redis Lua reservation before prediction creation. Losers return the existing job ID. Keep the reservation until a successful result is cached or the job has failed. | Add a concurrent POST check with the same two images; both responses must resolve to one job ID and only one prediction create call. |
| A user presses “Try another,” changes the garment, or starts another run while an older poll is resolving. The old result can be applied to the new UI selection or the old response can be spoken. | `src/app/page.tsx`, `src/components/LiveTryOn.tsx`, `src/components/VoiceAgent.tsx` | Give each UI try-on run a monotonically increasing run ID and bind the selected garment ID to it. Abort old polls and ignore results unless both run ID and garment ID still match. Do the same turn-ID check before voice log/history/speech updates. | Start a delayed job, change garment/reset, then resolve the old poll; the new selection stays visible and no stale speech occurs. |
| A tool or LLM reply says a look is ready before the persistent job record contains `succeeded` and its permanent image URL. | `python-agent/tools.py`, `python-agent/main.py`, `src/app/api/tryon/[id]/route.ts`, `src/lib/tryon-jobs.ts` | The voice tool returns “started” with its job ID only. Any readiness announcement must poll `GET /api/tryon/[id]` and speak success only after the durable job response is `succeeded` with `resultUrl`. | Hold the job record at `processing`; assert there is no ready announcement. Commit success and verify the following GET precedes the announcement. |
| Barge-in cancels speech but an already awaited tool call can still return and perform a side effect or update the action log. | `src/components/VoiceAgent.tsx`, `python-agent/tools.py`, `python-agent/main.py`, `src/app/api/voice-tools/[...tool]/route.ts` | Assign a turn ID and abort signal to each turn. Check the signal and turn ID immediately before and after each tool side effect and before applying its result. Configure the LiveKit turn to cancel its tool task on interruption; the Next route must not accept a stale-turn mutation. | Delay a tool response, interrupt, then resolve it; assert no preference, try-on, log, or speech update is applied for the interrupted turn. |
| A bare “yes” can be applied to a newer purchase/share proposal after the original proposal changes. | `src/components/VoiceAgent.tsx`, `src/components/ShareComposer.tsx`, `python-agent/tools.py`, `src/app/api/voice-tools/[...tool]/route.ts` | Bind every confirmation to an immutable pending-action ID and action type. Replace/expire that ID when the proposal changes; confirmation accepts only the matching ID. Keep purchases unavailable to voice tools; share publication remains an explicit UI action. | Propose A, replace it with B, then answer “yes” to A; confirm neither action runs. Confirm B by its displayed ID and check only B proceeds. |
| Two sessions/tabs can overwrite preferences between reading the current profile and writing the update. | `src/app/api/preferences/route.ts`, `src/app/api/voice-tools/[...tool]/route.ts`, `python-agent/tools.py`, `src/components/VoiceAgent.tsx` | Use profile versions and Redis compare-and-set. Return `409` plus the latest profile on conflict; refresh and ask the user to repeat instead of silently retrying stale content. | Send two writes with the same `ifVersion`; exactly one succeeds, the other receives `409`, and the stored version increments once. |
| The camera frame is captured while garment selection changes, so the POST can pair a frame with a different garment than the overlay displayed. | `src/components/LiveTryOn.tsx`, `src/app/page.tsx`, `src/app/api/tryon/route.ts` | At capture start, snapshot the garment ID, file, and current video frame before any await; submit the frame and that garment together. Keep garment selection locked for the capture handoff and show the captured garment in the pending run. | Change selection at capture time with a delayed frame encoder; assert the POST contains the snapped garment ID/file and corresponding frame. |
| Demo/live mode or demo state changes after a run starts, causing a cached demo response to be combined with live service results (or vice versa). | `src/app/page.tsx`, `src/components/LiveTryOn.tsx`, `src/components/VoiceAgent.tsx`, `src/app/api/tryon/route.ts`, `src/app/api/voice/route.ts` | Snapshot demo/live mode and demo-state hash at run start. Disable mode changes while that run is active and route every service call through that snapshot. | Start a delayed demo request, try toggling mode, and verify it stays in demo mode through completion; repeat for live. |
| A slow caption suggestion can overwrite text the user has already edited; repeated share saves can create multiple public posts. | `src/components/ShareComposer.tsx`, `src/app/api/share/route.ts` | Keep edited-field refs and never replace user-edited caption/hashtags with a late suggestion. Guard save with a synchronous in-flight ref and idempotency key so one click creates one post. | Delay caption API, edit while it is pending, then resolve it; edits remain. Double-click save and verify one record/image is created. |

## Verification coverage

- `npm test` covers stale run epochs, share action/result binding, and that every scripted offline utterance has a demo-state-keyed cache entry.
- `tests/browser/demo-offline.spec.ts` replays prerecorded speech and barge-in, saves a preference, replays the CV overlay, completes a cached try-on, and opens the share page and OG image. It passed in the current environment.
- `tests/browser/live-fallback.spec.ts` checks the visible Moss-offline and browser/text fallback with provider credentials absent. It passed in the current environment.
- The Redis atomic-reservation/CAS and Replicate read-after-write races require configured Upstash/Replicate services. The table’s request pairs and delayed-status scenarios are the manual checks to run once those services are configured; they were not simulated with an in-memory substitute.
- The voice UI has no purchase or voice-publish tool. Shopping only prepares results; saving a share is a separate UI action tied to a changing confirmation ID. No voice “yes” handler can initiate a purchase.
